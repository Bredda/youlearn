# Courses domain

Key files: `packages/content/src/*` (content schema, quiz rules, video allowlist, diff), `apps/api/src/lib/{courses,revisions,assets,asset-sweep}.ts`, `routes/writer/{courses,revisions}.ts`, `routes/{assets,review}.ts`, `packages/db/src/schema/{courses,groups}.ts`; UI in `apps/web/components/writer/*` (editor), `components/content/*` (chapter, quiz, video and diff views), `components/review/*`, page `writer/courses/[id]/compare`. For API and UI conventions see `youlearn-api` and `youlearn-ui`.

## Groups

Groups are the visibility mechanism: a user belongs to 0..n groups (`/api/me` returns them) and courses are tagged with groups. The built-in **"Commun"** group (`group.system`, created at startup, an admin-made group with that name is adopted) is visible to everyone but **implicit**: never a `user_group` row (the API refuses it), so it never grants write access; it cannot be renamed or deleted and is hidden from the user form and filters. A group used by a course cannot be deleted (`restrict` foreign key plus a clear 409).

## Courses

Writer area `/api/writer/*`. A course needs at least one group. An admin edits every course; a writer only those sharing one of their *explicit* groups, and may only add/remove their own groups: the others (other teams, Commun) stay untouched (`resolveGroupIds`, `assignableGroups`). Only admins put Commun on a course. A course published once is archived instead of deleted (`deletedAt`, admin only, its `course_group` rows removed so groups can be deleted, slug freed) and its slug is frozen; a never-published course is really deleted. Name, description, categories (free lower-cased tags) and cover are not versioned.

Listing: `GET /api/writer/courses` follows the server-side table pattern (`WriterCourseQuery`, filters on search, status, group, category) and also returns the filter options computed from the courses the user can edit.

## Revisions

`draft -> preview -> published -> deprecated` (+ `preview -> draft`); **at most one open revision (`draft` or `preview`, never both) and one `published` per course** (two partial unique indexes), any number of deprecated; creating or cloning while one is open gives 409 `OPEN_REVISION` (`openRevisionBlocker`). Publishing deprecates the previous published revision, and deprecating needs `confirm: true` (409 `CONFIRM_REQUIRED` otherwise; the UI shows a confirmation naming the revision). Published revisions never change; restoring an old one means cloning it into a new draft (`parentId`). Status changes lock the course row (`for update`). The business id (`key`, Docker-like `whispering_toucan`) is unique per course and immutable. Every revision carries a mandatory `purpose` (why it exists, asked when creating or cloning, shown in the history, the diff and the review). Contributors are snapshots (no FK) and must be recorded with `addContributor` on every content change. A draft **and a revision in review** can be edited (the writer fixes as remarks come in, `isEditable`) and deleted; `preview -> draft` only means "withdraw from review".

## Content and files

A revision holds its content as a versioned jsonb manifest (`course_revision.content`, `CourseContent` **v2**, defined and validated by `@youlearn/content`): ordered **chapters**, each with ordered **blocks** (`markdown`, or `video` = a YouTube/Vimeo link, https only, the embed URL is derived by `parseVideoUrl` and never stored) and an optional **quiz** that is always last. A quiz draws `drawCount` (n) questions from its pool of m (`1 <= n <= m`), is `blocking` or not (a blocking quiz locks the **next chapter** until `passRate` % is reached; enforced by the server, see "Learner journey"), and holds `single` / `multiple` choice questions (2-10 options, markdown prompt and explanation). Each chapter also carries an optional `estimatedMinutes` (1-1440) set by the writer; `courseDurationMinutes`, `chaptersMissingDuration` and `formatDuration` (`@youlearn/content`, pure) sum, check and display it. Saving a draft never requires it, but **a draft cannot go to `preview` while a chapter has none** (`previewBlocker` in `lib/revision-rules.ts`, 409 `INCOMPLETE`). A course can be **certifying** (`content.certifying`, versioned with the revision): it then has exactly one chapter with `kind: "final-exam"`, always the last, holding only a quiz (no blocks; its `passRate` always counts, `blocking` is irrelevant), enforced by `contentSchema`. The editor's "Cours certifiant" switch adds it (`newFinalExam`) and turning it off removes it; the reducer refuses to move, remove or fill the exam. Both additions are optional fields, so `CourseContent` stays **v2** and old revisions stay valid. `course_revision.durationMinutes` and `.certifying` are derived from the content in `saveContent` (and copied when cloning) so lists and the catalog never read the jsonb. **Every id (chapter, block, question, option) is stable**: the editor never regenerates one and cloning keeps them, because the diff pairs items by id. Saves use optimistic locking (`expectedUpdatedAt`, 409 `STALE`, body limit raised to 8 MiB on that route), record a contributor, and log no event. Cloning copies the manifest.

**Quiz answers (`correct`) never reach a learner**: a learner only receives `LearnerContent` (`toLearnerContent`: the quiz keeps its settings and the pool size, no question), the drawn questions come from an attempt without `correct` nor explanation, and grading happens on the server. Writers and reviewers see the full content.

**Diff** (`diffContent` in `@youlearn/content`, pure): chapters, blocks, questions and options paired by id, `added | removed | modified | unchanged` plus a separate `moved` flag (items whose order among the common ones changed), line hunks for markdown (`diffLines`, words via `diffInline`), a flipped correct answer flagged on options, `durationChanged` per chapter and `certifyingChanged` for the course. Heavy files are compared by asset id (assets are content-addressed). No API: both contents come from the existing `GET .../revisions/:revisionId` (any status, deprecated included, editors only). The same `RevisionDiff` view serves the editor (live, against the parent), the compare page (`/writer/courses/:id/compare?from=&to=`) and the review (switch, off by default).

Files are `course_asset` rows (per course, deduplicated by `sha256`, blob at `courses/<courseId>/assets/<sha256>`, never rewritten); blocks, prompts and explanations reference them as `asset:<id>` in markdown (the sweep and `revisionUses` match that substring in the serialized jsonb: keep that form) and the cover is `course.imageAssetId`. Everything goes through the API: upload `POST /api/writer/courses/:id/assets` (images only, type sniffed from the bytes, SVG refused, 5 MB), download `GET /api/courses/:id/assets/:assetId` (`Range` supported so videos can reuse it; large uploads will need presigned URLs).

**The app never deletes a file for good**: `moveToDeprecated` copies it to the deprecated bucket (`S3_DEPRECATED_BUCKET`, default `<S3_BUCKET>-deprecated`, same key) then removes the original; purging that bucket is an ops decision. Archiving a course leaves its files in place. Hard-deleting a never-published course moves its files, and `lib/asset-sweep.ts` (at API startup, then every 6 h) moves the files of living courses that no revision references (any status, deprecated included) and that are not the cover, once older than 24 h (an uploaded image may not be saved yet).

## Reviewers and file access

There is **no reviewer role and no review link**: a reviewer is an assignment, `revision_reviewer` (revision, user; FK with cascade), written by the editors of the course. Sending a draft to review needs at least one reviewer (`POST .../status {to: "preview", reviewerIds}`, 409 `NO_REVIEWER` otherwise; the ids replace the current ones, omitted keeps them, they must be existing non banned users, at most 20); `POST .../reviewers {userId}` and `DELETE .../reviewers/:userId` change them while the revision is in preview (the last one cannot be removed); `GET /api/writer/reviewer-candidates?q=&exclude=` feeds the picker (any active user, by name or email). Being assigned gives read access **only while the revision is in `preview`**: `GET /api/me/reviews` lists the user's pending reviews and `GET /api/reviews/:revisionId` returns the revision read-only with its `purpose` and a `base` (its parent when that one is published or deprecated, never somebody's unpublished work) so the reviewer can toggle the diff; anyone else, and a review that is over, gets 404. The rows stay as history after the revision moves on, and going back to draft then to review again keeps the reviewers. Events `revision.reviewer-add` / `-remove` (the old `new-link` / `revoke-link` types stay registered only so past rows keep their labels).

Web: `/reviews` (list, the sidebar entry "Relectures" with a count only shows when something is pending, fetched in the `(app)` layout) and `/reviews/[revisionId]` (`ReviewViewer`); the writer picks reviewers in `ReviewersDialog` (from a draft it goes with the status change, in review each add/remove is immediate).

`canReadAsset`: editors read every file of their courses; everybody else only the cover and the files used by the published revision (when they can view the course); a **reviewer** also reads the cover, the files of the revision they review **and of its base** (so an image that was replaced still shows in the diff), even outside the course's groups; a learner reads those of the revision they follow. Draft files stay private even inside the course's groups.

## Learner catalog

`GET /api/courses` (`lib/catalog.ts`, `routes/catalog.ts`, any signed-in user) lists what a learner can see: living courses with a **published** revision tagged "Commun" or with one of the user's *explicit* groups. Writers get the same learner rule (their view of unpublished work is the writer area); an **admin sees every published course**, whatever its groups, and can filter by any non-system group. Item shape `CatalogCourse` (with `durationMinutes` and `certifying` of the published revision, shown on the card) carries no group list (it would leak other teams' names); `publishedAt` is the `updatedAt` of the published revision (it never changes afterwards). Filters: search (name, description), category, and one of the user's own groups (any other group id yields nothing); sort `name` or `publishedAt`. The filter options are the visible categories and the user's own groups (an admin: all non-system groups). Each item also carries `enrollmentStatus`, the status of the user's **most recent** enrollment on the course whatever its revision (null when never started; a correlated subquery in `lib/catalog.ts`), and the catalog filters on it with `status` (`in_progress | completed | failed | none` for never started). Web: `/courses` (card grid, `components/catalog/*`, a status badge on the card), each card links to the course sheet `/courses/[id]`.

## Learner journey

Tables in `packages/db/src/schema/learning.ts`: `enrollment` (learner, course, **pinned `revisionId`**, status `in_progress | completed | failed`; a partial unique index allows a single non failed enrollment per learner and course), `chapter_progress` (finished chapters, by stable chapter id) and `quiz_attempt` (the draw kept as jsonb, the answers, score, `passed`; a partial unique index allows **one final exam attempt per enrollment**). Pure rules live in `@youlearn/content` and are tested: `toLearnerContent`, `chapterStates` / `canCompleteChapter` / `enrollmentOutcome` (`progress.ts`), `drawQuiz` / `learnerQuestions` / `answersIssue` / `gradeAttempt` (`quiz-draw.ts`). DB access is in `apps/api/src/lib/learning.ts` (learner side) and `lib/enrollments.ts` (lists), routes in `routes/learning.ts` and `routes/writer/enrollments.ts`.

- **Sheet and enrollment**: `GET /api/courses/:id` (same visibility as the catalog) returns the chapters and the learner's latest enrollment; `POST /api/courses/:id/enroll` pins the revision published now (409 `ALREADY_ENROLLED` while a non failed enrollment exists, 404 when the course is not visible). Enrolling after a failure starts from scratch on the revision published at that moment (event metadata `restart`). A newer publication never moves an enrollment: `outdated` only drives a banner.
- **Revision history on the sheet**: `LearnerCourse` carries `revisionKey` (the published one) and `revisions`, the revisions that were published or deprecated, most recent first (deprecating bumps `updatedAt` and one revision is published at a time, so that is the publication order), each with its `purpose` and the learner's latest `enrollmentStatus` on it. Drafts and revisions in review are never listed. The web opens it from a button on the sheet (`RevisionHistory`, a side sheet) with a mark facing the revisions the learner completed, follows or failed.
- **Player**: `GET /api/enrollments/:id` (owner only, 404 otherwise, even for an admin; the visibility of the course is rechecked with `canViewCourse`). It returns `LearnerContent` of the pinned revision, `chapterStates`, `passedQuizzes` and the attempts. **A locked chapter is sent without its blocks.** `canReadAsset` also lets a learner read the files of the revision they follow (even deprecated).
- **Progress rules**: a blocking quiz keeps every later chapter locked until passed; the final exam stays locked until all other chapters are completed; a chapter is finished by `POST .../chapters/:chapterId/complete` (needs the blocking quiz passed; the final exam is never finished by hand). The enrollment completes when every chapter is completed. Mutations lock the enrollment row (`for update`); a `completed` or `failed` enrollment is read-only (409 `NOT_ACTIVE`).
- **Quizzes**: `POST .../chapters/:chapterId/attempts` draws n of m questions and keeps the draw, or resumes the open attempt; `POST .../attempts/:attemptId/submit` validates the answers (400) and grades them: a question is right when the ticked options are exactly the correct ones, score = % of right questions, passed when `score >= passRate`. A chapter quiz returns the correction (right options, explanations), can be retried and a new attempt gets a new draw. **The final exam is one attempt and never returns a correction**: passing it completes the enrollment, missing it sets `failed` (events `enrollment.complete` / `enrollment.fail` with the score).
- **Traceability**: `GET /api/me/enrollments` ("Mes sessions", only courses the learner can still open); `GET /api/writer/courses/:id/enrollments` (+ `/:enrollmentId` for the chapters and every attempt) for the people who edit the course (`authorizeCourse`, an admin sees all) with the learner's name, email, progress and final exam score. Events: `enrollment.start`, `.complete`, `.fail`; chapter completions and chapter quiz attempts log nothing (the tables are the trace).

## Not built yet

Certificates (a `certificate` table with a snapshot of learner, course, revision key, score and date, a PDF rendered on demand with pdf-lib, a public `/verify/<number>` page), moving an enrollment to a newer revision, re-enrolling after a success (or a validity date that forces a retake), programs, uploaded videos (only YouTube/Vimeo embeds exist) and large uploads.
